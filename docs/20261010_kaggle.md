# Kaggle T4×2 Remember 실험

두 모델을 합친15시간 제한 안에서 원본 RMT 설정에 가까운 비교를 한다.
원본 출처는 `24cbb9aed62a5748c4045fd928f7f59899f03b24`의
`scripts/associative_retrieval/finetune_rmt_ar-value_cur.sh`와 논문 Appendix E다.

- 원본 D128 / 4층 / FF128 / memory32, V128, key/value 원소0…15, value 길이1.
- 원본 train100만 / validation1000 / test10000, random-length curriculum과 full BPTT.
- 원본 effective batch512, AdamW lr3e-4 / weight decay.001 / value clipping1.0.
- 후보: 원본의 첫7단계, pairs1/2/3/5/10/20/40; key sizes1/1/1/1/1/2/2.
  두 모델 사전 측정 후 시간 안에 원본 예산을 완료할 공통 prefix를 선택한다. 기본 예상은20쌍까지다.
- 단계별 최대 업데이트2000/10000/10000/10000/10000/10000/10000.
- 두 GPU를 한 모델의 데이터 병렬 학습에 사용하고 RMT→GRT 순차 실행한다.
  GPU별 microbatch×accumulation×2=512를 유지한다. VRAM은 합산되지 않는다.
- 모델별 학습6.5시간 상한, 평가·저장 포함7시간 상한, 준비/측정 등을 포함 전체15시간 상한.
  원본200쌍 전체 학습의15시간 완료나 모든 단계의 수렴을 보장하지 않는다.
- 원본 최대 업데이트를 완료한 뒤 다음 단계로 진행한다. 고정 길이 EM99%는 성공 여부를
  기록하며 조기 전환에 쓰지 않는다. 시간 중단과 정상 예산 완료를 구분한다.
- GRT의 router/ALU/write-back은 유지한다. key 길이 변화 시 가중치 전달이 가능하도록
  이번 실험만 local position5개를 처음부터 확보하며 새 위치를 중간에 재초기화하지 않는다.
- FP32를 기본으로 한다. 원본의4GPU 대신2GPU, 추가 fixed-length 평가, 시간 상한을 사용한다.

사전 측정은 실제 학습 CLI의 benchmark 모드로 각 모델/단계의 gradient·AdamW update,
peak VRAM, 짧은/최대 길이 시간을 확인한다. 초기 RMT 실측(B1024,2쌍)의 약.53s/update를
선형 환산하면2GPU의 global512에서20쌍까지 약4시간,40쌍까지 약7시간의 학습 비용이다.
이 값은 통신·평가·데이터 준비를 제외한 추정이며 GRT에 그대로 적용하지 않는다.
실제 Kaggle 측정과 시간 상한으로 실행하며 원본 업데이트 수를 유지할 공통 단계 범위를 선택한다.

최대 길이 메모리는 sequence 평균이 아닌 최대 pairs+query로 산정한다.
RMT 실측을 기준으로 GPU별 microbatch256×21segments와128×41segments는 대략9GiB 수준이다.
모델별 사전 측정에서 확인하고 microbatch를 줄일 때 accumulation을 늘려 global512를 유지한다.
아래에 전체 예산·실행 방법·CPU 검증 결과를 기록했다.

## 시간·과제 범위

평균 fact 수는 random-length uniform(1…P)의 `(P+1)/2`이며 query를 포함한
평균 segment 수는 `(P+3)/2`다. 기존 RMT의 B1024, 평균2.5segments,
약0.53초/update 관측을 선형 환산하면 두 GPU의 각 B256에서 segment당
약 `0.53 × (256/1024) / 2.5 = 0.053초`다. 따라서
`Σ(stage_updates × (P+3)/2 × 0.053)`은20쌍까지 약4.1시간,
40쌍까지 약7.3시간이다. 40쌍까지 원본 최대 업데이트를 모두 소진하기에는
6.5시간이 부족할 수 있어 후보 전부를 무조건 실행하지 않는다. 기존 관측에서의 환산일 뿐 T4×2 실측 완료 시간이 아니다.
GRT에 같은 속도를 가정하지 않는다. 사전 측정은 실제 AdamW·분산 gradient 통신과
원본 collator 비용을 포함하며 준비·저장·최종 테스트·운영 오버헤드는 별도다.

2쌍에서는 한 fact만 출력하는 전략도 value가 우연히 같을 경우를 포함해
`1/2 + (1/2)/16 = 53.125%` 성공할 수 있다. 40쌍에서는 같은 전략이
`1/40 + (39/40)/16 = 8.594%`다. 여러 fact에서 query key에 대응하는 value를
찾는 기능과 길이 증가를 확인하기 위해1→40쌍을 목표로 한다. memory32개가
40개 연관을 반드시 저장하지 못한다는 뜻은 아니며 한 register에 여러 정보를
분산해 표현할 수 있다. 두 모델의 훈련 목표는 같은 prefix이며, 예기치 않은 시간 중단으로 완료 단계가 다르면
공통 완료 범위에서 비교한다.

학습 종료 시 best checkpoint로 학습 길이에서 test10000개를 평가하고,
1/2/3/5/10/20/40/50/100/200쌍을 각각1000개 평가한다. 이 추가 평가는 checkpoint의
key 길이를 유지한다. key2의 unique key 공간256 안에서200쌍이 가능하지만,
원본200쌍 단계는 key3이므로 **원본200쌍 실험의 직접 재현 지표가 아니다.**
key1 단계에서 중지하면16쌍을 초과하는 평가를 incompatible로 기록한다.

## 실행과 기록

`notebooks/kaggle.ipynb`에서 checkout/output 경로를 지정하고 Run All한다.
Internet와 GPU T4×2를 선택한다. 최신 노트북과 범용 template 두 개만 유지한다.
모델별 사전 측정으로 microbatch/accumulation을 정하고, 두 모델에서 시간 내에
완료 가능한 가장 긴 공통 prefix를 선택한다. 원본 단계의 key 크기·업데이트 수는 유지한다.
계산은 `1.25 × 예상 학습/검증 시간 + 데이터 생성600초 ≤ 학습23400초`로 하며,
모델별 잔여 시간에서 최종 평가1200초도 확보한다. 두 모델의 예상 비용·여유 시간 합계도
전체 잔여 시간 이하여야 한다. 실제 측정에 따라20쌍 또는40쌍 등으로
계획이 확정되고 재개할 때 같은 계획을 유지한다.
초기 GPU별 B256×1, 40쌍 B128×2는 둘 다 global512다. VRAM80%를 넘기거나
OOM이면 microbatch를 줄이고 accumulation을 늘린다. global512로 microbatch의
상한이 정해지므로 작은 단계에서 남은 VRAM을 채우려고 global batch를 늘리지 않는다.

수동 실행은 아래 공통 CLI를 사용한다. GRT는 `configs/rmt.yaml` 대신
`configs/grt.yaml`을 사용하고 `configs/kaggle_grt.yaml`도 함께 병합한다.
시간 예산과 사전 측정을 함께 운영하려면 노트북을 사용한다.

```bash
python -m torch.distributed.run --standalone --nproc_per_node=2 scripts/train.py \
  --config configs/base.yaml configs/rmt.yaml configs/kaggle.yaml \
  --output-dir /kaggle/working/remember_rmt --device cuda
```

- `experiment_plan.json`: 두 모델의 공통 단계·원본 업데이트 예산·실측 예상 시간.
- `execution.json`: 전체·모델별 실행/중단/누적 시간. 노트북은 시작 시각부터15시간을 계산한다.
- `<model>_preflight/benchmark.json/.txt`: 최대 길이 peak와 업데이트/평가 시간, 단계별 예상 비용.
- `<model>/summary.json/.txt`, `evaluation.json/.txt`, `length_evaluation.json/.txt`, `convergence.png`.
- 각 stage: `metrics.jsonl`, `metrics.txt`, `resolved_config.yaml`, `metadata.json`, best/last checkpoint.
- console/preflight TXT에도 subprocess 출력을 저장한다. W&B 기본 true, Kaggle Secret `WANDB_API_KEY`로 로그인하고 rank0만 기록한다.

trainer의6.5시간은 데이터 준비·학습·validation을 포함한다. 최종 평가·저장은 모델별7시간
외부 제한 안에서 수행한다. 중단 시 마지막 저장 checkpoint를 보존하며 강제 종료는
최근 저장 이후 update를 잃을 수 있다. `completed`는 예정 업데이트 실행 완료를 뜻하며 기능 성공은 fixed EM99%와 test 지표로 판단한다.
kernel/시간 중단으로 최종 평가 파일이 없으면
완료로 간주하지 않는다. 동일 config/output/두 프로세스로 잔여 시간 내 재개한다.
중단된 kernel의 실행 시간은 보수적으로 예산에 포함한다. 실행 예산 파일을 초기화하여
제한을 연장하지 않는다. Kaggle output은 Save Version으로 보존한다.

## 구현과 CPU 검증

이번 설정의 파라미터 수는 RMT435,456 / GRT847,680이다.
원본 vendor 파일은 변경하지 않았다. DDP 내부에는 loss만 반환하는 작은 경계를 두어
원본이 HF 출력에 추가하는 `ce_loss` 필드의 pytree 복원 오류를 처리한다.
학습은 native forward/loss를 호출하고 checkpoint는 기존 native state_dict prefix로 저장한다.
평가·생성도 native 모델을 직접 사용한다. global 배치를 한 번 collate한 뒤 rank별로
나누므로 원본의 배치 단위 random length를 유지한다. 마지막 작은 배치는 실제 샘플 수로
loss를 가중하며 DDP 평균 후 gradient value clipping·AdamW·scheduler 순서를 유지한다.

학습·평가·로그·checkpoint/재개를 실제 `scripts/train.py`로 두 CPU 프로세스에서 검사했다.
RMT/GRT 모두1쌍/key1→20쌍/key2, gradient accumulation, 작은 마지막 학습 배치,
rank별 평가 샘플 수가 다른 경우, 길이1/20/40 평가와 분산 checkpoint 재개를 통과했다.
동일 global batch의 단일 프로세스와 최종 평가 loss 차이는2e-6 미만이며,
같은 두 프로세스로 checkpoint를 재개한 최종 가중치는 정확히 일치했다.
GRT attention key bias에는 softmax 불변 방향의 거의0인 gradient가 AdamW에서
확대되는 FP32 roundoff 차이가 있어, 단일/분산 가중치 비교에서 해당 항목만 별도로 허용했다.

두 모델의 실제 CLI benchmark, 동기화된 시간 중단, 호환 불가능한 길이 skip,
노트북 subprocess 강제 종료와 시간 기록도 CPU에서 검사했다.
기존·분산 CPU 검사32개와 최신 노트북 통합 검사1개가 통과했다.
노트북은 GPU와 데이터/모델 규모만 CPU용으로 바꾸어 사전 측정→공통 계획→
두 모델 실제 분산 학습 CLI→최종 평가·그림 저장까지 직접 실행했다. GPU/NCCL·T4 VRAM·처리량·수렴은 이 환경에서 실측하지 않았으며
Kaggle 사전 측정과 사용자 실험 결과로 확인한다.
